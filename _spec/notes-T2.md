## 1. 十二招各自的起手式与命中姿势（P1-5）

### 做法
`figure.js` 新增 24 个 pose：`<id>_wind` / `<id>_hit`，`tech.js` 的 26 处 `cast()` 全部改指过去。
**现有 pose 名一个没改、没删**（T3 的敌人在引用），只增。
`castWind` / `castHit` 原样保留 —— bosses.js 有 6 处在用。

差别一律做在**大动作**上：重心高低、手臂朝向、腿的开合、剑尖落点。
理由：游戏里主角 `scale = 0.86`（≈55px 高），手腕角度那一级的差别全糊掉了，只剩轮廓。

| 招 | 字 | 起手 | 命中 |
|---|---|---|---|
| 横云断 | 横 | 剑水平收到身后胸高 | 同一条水平线贯到身前，后腿蹬空 |
| 裂帛 | 裂 | 剑竖在身前正中，双手都在中线 | 前手斜上、后手水平向后，撕成「V」 |
| 撑天 | 撑 | 弓步压到最低，剑垂在后下 | 剑直指正上，全身拉成一条竖线 |
| 孤影 | 孤 | 团到最小，剑横收在身侧 | 贴地侧伏，一手撑地（全场最矮最扁） |
| 无锋 | 无 | **剑竖直垂在体侧、尖点地**，并步直立 | 双手齐推，剑水平，身体仍然中正 |
| 连环腿 | 连 | 高提膝（腿是主角），剑收在身后 | 前腿踢过胸口，脚在全身最高处 |
| 破雨 | 破 | 肘收到腰侧压紧，剑贴身水平 | 全场压得最低的一记直刺 |
| 穿杨 | 穿 | 后手拉到耳后（拉弓），侧开步 | 后手放开甩到身后，人向上弹起 |
| 镇山 | 震 | 腾空收腿、双手把剑举到最高 | 砸成一团深蹲，剑尖插进地里 |
| 踏云 | 提 | 空中收拢，剑斜举 | 一腿向下猛蹬，拉成向上的箭头 |
| 焚书 | 分 | 含胸下沉马步，双臂环抱、剑横抱怀里 | 反向撑开（前手向后、后手向前下） |
| 说剑 | 说 | 剑 45° 斜指前上「引」，后手负于身后 | 跨度最大的一记斜劈，从后上切到前下 |

「无锋」那一条是全表里最得意的一处：它是唯一一个**剑尖朝下**的起手式。
一个不指向任何人的剑，比任何注释都更直白地说明这一招不造成伤害。

### 判据（不是「看着还行」）
把 pose 解算成 15 个关节（含剑尖）的坐标，两个姿势的差异用 **RMS 位移**衡量，
单位是 figure.js 的局部单位（`scale=1` 时身高约 62），阈值定 **10 ≈ 身高的 16%**。

| 项 | 改造前 | 改造后 | 阈值 |
|---|---|---|---|
| 12 招起手两两最接近的一对 | —（12 招共用一个 pose，恒为 0） | **12.1**（穿杨/说剑） | ≥10 |
| 12 招命中两两最接近 | —（同上） | **10.6**（横云断/踏云、横云断/说剑） | ≥10 |
| 同一招 起手→命中 | —（同上） | **10.3**（穿杨） | ≥10 |
| atk1/2/3 六个姿势两两最接近 | **4.1**（atk2_wind vs atk1_hit） | **16.1** | ≥10 |

**起手那条（12.1）是任务书要的，余量舒服；命中那条（10.6）是我自己加的，余量只有 0.6。**
如果以后有人微调姿势把它撞红了，先看是不是真的撞脸，再考虑降阈值 ——
我试过为了拉开 RMS 去推横云断的躯干，结果它离说剑更近了（10.6→10.2），
那就是在拟合指标而不是在改剪影，退回来了。

另外量过一版「用剑尖距离代替全身 RMS」：**不行**。裂帛与踏云的起手剑尖只差 3.7 单位
（两个都是剑朝上），但一个站着、一个在空中团着，全身 RMS 14.5，一眼就能分开。
剑尖只是 15 个关节里的 1 个，全身 RMS 才是对的度量。

阈值和实测值都写死在 `dev/player-check.js` §9。**这条断言的价值在于：
共用一个 pose 是不报错的**，玩家只会觉得「这游戏的招都长一样」，
在这之前没有任何自检会亮红灯。

### ⚠️ 一个只有量了才知道的坑：`_hit` 姿势有可能**永远走不到**

`player.js` 的 cast 进度是 `prog = p.st / 0.3` 写死的。招式全长不足 0.3s 的，
它的 `_hit` 姿势就只能走到一部分 —— **不报错、不告警，就是永远摆不出那个造型**。
实测每一招在 cast 里能走到的最大 prog（`node /tmp` 里那个探针，结论抄在这）：

```
踏云 0.28 ← 只走了不到三分之一      孤影 0.72   说剑 0.90   破雨 0.94   镇山 0.94
无锋 1.00   撑天 1.17   裂帛 1.22   焚书 1.44   连环腿 1.67   穿杨 1.72   横云断 1.78
```

- **孤影 0.72**：`ease(0.72) = 0.978`，实质上已经走满，不用管。
- **踏云 0.28**：真的走不到，已修 —— `tiyun_hit` 内部把进度 ×3 提前跑满。
  顺带修掉了它的第二个毛病：末帧 `setState('jump')` 时会从「剑举过顶」一帧掉成
  「手垂下的起跳蹲」，实测那一帧关节跳变 **RMS 33.0**（改造前 rise→jump 只有 11.8）。
  把收势的手臂朝 jump 的位置靠之后降到 **16.7**。仍比 11.8 大，但 `tiyun_hit` 本来就
  比旧的 `rise` 是个更远的造型，而且那一帧人正以 640px/s 上飞，遮得住。

**踏云是全表唯一一个 cast 全长 < 0.3s 的招**，所以只有它需要这个处理。

### 「传错不报错」的两道闸
`SJ.Figure.pose('hengyun_wnid')` 只会 `console.warn` 一次，然后**永远退回 idle**。
所以 §9 加了两条：
- **静态**：正则扫出 tech.js 全部 26 处 `cast(p,'X')` 和 player.js 的 8 个字面量 pose 名
  （加上三连拼接出来的 9 个 `atkN_phase`），逐个查 `Figure.poses` 里在不在。
- **动态**：把 12 招真的跑一遍，劫持 `console.warn`，出现任何一次「未知 pose」即失败。

顺带补一条：`tech.js` 里不许再出现 `cast(p,'castWind')` / `cast(p,'castHit')`——
把「12 招雷同」的根因本身钉成断言。

## 2. atk1 / atk2 / atk3 剪影分离（P1-6）

三段是三个**方向**，不是三个力度：

- **atk1 横**：起手剑水平收在身后胸高（剑尖 x=-51），命中同一条线贯到身前（x=+56），肩线不动。
- **atk2 斜**：起手剑压到后下贴地（剑尖 y=-10，几乎在地面），命中撩到前上方（y=-83，过头顶）。
- **atk3 竖**：起手举过头顶（剑尖 y=-97），命中劈到脚边（y=-2），重心从最高砸到最低。

E 自报的「atk1/atk2 姿势过近」实测确认了：改造前 `atk2_wind` 与 `atk1_hit` 的 RMS 只有 **4.1**。
现在六个姿势两两最小 **16.1**。

### ⚠️ 给 T3 的一条：别名会跟着动
`upslash` 与 `downslash` 在 figure.js 里是 **`atk2_hit` / `atk3_hit` 的引用别名**，不是拷贝。
我重塑了 atk2_hit / atk3_hit，所以 enemies.js / bosses.js 里所有用到
`upslash` `downslash` `atk1_*` `atk2_*` `atk3_*` 的地方（共 8 处 `poseA/poseW/poseR`）跟着变了。
**我认为应该跟着变**：撩＝向上、劈＝向下，改完只是更贴字面，敌人的动作也更清楚。
如果 T3 觉得某个敌人因此不对劲，说一声，我可以把别名冻成今天形状的拷贝——
但那样敌人就永远停在旧剪影上，不建议。

## 3. 命中确认四档（P1-7）

`combat.js` 新增 **`SJ.Combat.TIER`**（只读表）。五个轴逐档**严格递增**：

| 档 | key | hitstop | 震幅 | 墨点数 | 甩出力度 | 音量 | 触发路径 |
|---|---|---|---|---|---|---|---|
| 轻击 | `light` | 45ms | 3.0 | 3 | 180 | 0.70 | 普攻前两段 / `weight:'light'` / 伤害 <9 |
| 重击 | `heavy` | 90ms | 7.0 | 8 | 320 | 0.85 | 招式命中 / `weight:'heavy'` / 伤害 ≥14 |
| 完美格挡 | `parry` | 100ms | 10.0 | 12 | 400 | 0.95 | 观势读中（`parryFx`） |
| 处决 | `execute` | 140ms | 13.0 | 16 | 480 | 1.00 | `weight:'huge'`（镇山、说剑重斩、Boss 破防） |

**hitstop 一个数都没动（Δ=0ms），手感不变。** 分层做在另外四个轴上：

- **改造前这四档在震幅/墨点/音量上几乎分不出来**：音量是 `0.8 / 1.0 / 1.0 / 1.0`——
  四档里三档一个值；完美格挡的震幅（7）比重击（8）还小；甩速是
  `200 + 震幅×20` 推出来的，parry 那条路径干脆写死 300。
  停顿是唯一有层次的轴，而停顿恰恰是最不该动的那个。
- **震幅峰值仍然是 13**，没有引入新的最大值（3 → 7 → 10 → 13，重击从 8 降到 7 换来间距）。
- **音量整体下调**：轻击 0.8→0.70、三连第二段 1.0→0.78、重击 1.0→0.85。
  处决与格挡维持最响。这是**听得出来的变化**，一顿乱砍不再和一记重斩一样吵。
- 「完美格挡比重击更重」是有意的：格挡是玩家做对了一件难事，那一下要比他自己砍中更响。
  格挡后额外挂的半拍 0.25× 慢镜是格挡独有的「回味」，不属于四档。
- **伤害 / 帧数 / 判定框一个字没动。**

### 怎么验的
不是「表里写着这些数」，而是**这些数真的传到了 FX 与 Audio**。
spy 住 `Game.slowmo` / `Game.shake` / `FX.splash` / `Audio.sfx`，四条路径各跑一次，
逐档确认五个参数全部出现在调用参数里。
判据是「其中**有一次**等于该档」而不是「只有一次」——镇山(.14)/焚书(.12)/无锋 onHit(.14)
自己也会调 slowmo 与 shake，`slows` 取最小 scale 不会叠时长，但 spy 会看见多次。

Lead 的「每档不得比现状多 30ms」约束以字面量基线钉在 `player-check.js` §10。

### `mid` 为什么留着
`WEIGHT.mid`（60ms）**不是第五档**，是三连第二段的过渡：45→60→90 才能拉出
「第三下明显更重」。notes-E 记过实测——第三下拖到 110ms 会把连段切成三次独立挥砍。
删掉它会直接打掉「hitstop 逐段递增 45→60→90ms」那条既有断言。

## 3b.「挡开」—— invuln 目标的回馈（T3 发现，Lead 追加）

改造前 `strike()` 的无敌分支是 **`if (e.invuln > 0) return;`**：静默吃掉 hitbox，
没停顿、没墨点、没声音。**「什么都没发生」和「挥空了」在屏幕上长得一模一样**，
玩家没法学。Boss 换势（ai.js 的 shift 态）有 1.0–1.3s 无敌，这时候一顿砍下去毫无反应。

`SJ.Combat.DEFLECT`：

| 参数 | 值 | 理由 |
|---|---|---|
| hitstop | **0** | 换势期间玩家可能连着砍中七八下；哪怕一帧一次也会糊成一片粘滞 |
| 震幅 | 2.0 | 比轻击（3.0）还轻——这一下不算数 |
| 视觉 | 淡墨环 + 一笔短横 | **不飞墨点**：墨点是「见血」的语言，这一下没见血 |
| 音 | `block`，音量 0.55 | 全场最轻的一声 |
| 进度 | 不给 | `Tech.gain` 在这条分支之后，天然走不到；断言钉死 |

**不是第五档**：四档说的是「这一下有多重」，挡开说的是「这一下不算数」。
`hb.silent`（无锋）仍然静默——那一招本来就不该出声。

**单向**（Lead 裁定）：只在**玩家的攻击被无敌目标吃掉**时出现（`!isPlayer`）。
玩家自己在受击无敌 0.6s 或身法无敌里被打时保持静默 ——
那不是「挡住了」，那是无敌帧；响一声 block 等于告诉玩家「你挡住了」，
会把他往错的方向教（真正的「挡」是观势格挡，有完全不同的一整套反馈），多敌围攻时还吵。
我第一版做成了双向，理由是「同一条因果对玩家也该可见」；Lead 的反驳我接受，
因为那条因果**不是同一条** —— 一边是「你打不动他」，一边是「你现在无敌」，
用同一个反馈去说两件事本身就是在教错。两条断言分别钉住受击无敌与身法无敌都必须静默。

## 4. 预警分层的绘制（决议 014 **修订版**）

`SJ.Combat.telegraph({ ..., tier })`，取值 `light|heavy|grab`，缺省 `light`，**拼错也退回 light**。
`path / dur / danger / color` 语义一个字没动，「能不能格挡」的规则不变。

| tier | 画法 | 观势时 | 不观势时 |
|---|---|---|---|
| light | **朱砂 ×1.0 单笔 —— 与改造前逐位相同** | 3.4 | 每段 2.8 |
| heavy | 朱砂 **×1.6** + 路径端点一个**实心朱砂「势」点** | 5.44 + 势点 | 每段 4.48 + 势点 |
| grab | 朱砂主线 + **外圈淡墨线**（双线） | 主线 3.4 + 外圈墨色 | 每段主线 + 外圈成对 |

**分层往「更重」做，不往「更淡」做。** 我第一版按决议原文把 light 降成了墨线，
Lead 改了决议：墨线画在墨画的世界里显著性掉一截，而玩家玩了两回已经学会
「红线 = 来招」，把普通招降成墨线是拿可读性换分层，方向反了。修订版已落地。

- 「不传参画面不变」这条重新成立，并且**写成了断言**：
  `light` 的颜色与线宽以字面量（`#b03a2b` / 3.4 / 2.8）钉在 `player-check.js` §11，
  而且额外断言「不传 tier 画出来的东西与 light 完全一致」。
- 端点那个**实心「势」点**是 heavy 的关键。只靠线宽 ×1.6 在 0.3s 内是分不出来的。
  用 `SJ.Ink.blob`（真的墨团）而不是几何圆——既是水墨的语言，也让断言看得见它。
- **颜色只由 `danger` 与显式 `color` 决定，tier 完全不参与**，
  于是「落点小点跟 danger 走、不随 tier 变」这条自动成立，不需要额外的特判。
- 守势型（`danger:false`，守阁人）不吃 tier：石青、线宽不变、无势点。
  它根本不会打人，画成朱砂加粗或双线等于骗玩家躲一记不存在的招。
- 显式 `o.color` 仍然优先（bosses.js 在用）。
- **不观势的断续画法也分层**（含势点）。这一条是有意的：REVIEW 要的是
  「玩家能在 0.3s 内决定挡还是闪」，只在观势时分层的话，这个能力在最需要它的时候不存在。

### 决议 025 的两处细调（T3 动态验证后 Lead 裁定）

1. **势点提前长出来**：原来从 p=0 起淡淡地长（r 3.6 / alpha 0.30），
   中段和 light 分不开，等看得出来时已经是末段、来不及决定挡还是闪。
   改成 **p<0.25 不画、p≥0.25 那一帧直接以 r=4.6 / alpha=0.44 出现**，再按 p 线性长满
   —— 「出现」本身就是信号，比「慢慢变浓」快得多。
   线宽 ×1.6 本来就与 p 无关、第一帧即生效，补了断言钉死。
2. **grab 落点外环下限 22px**：原式 `32(1-p)+17` 在 p>0.84 之后收到 17px，
   和内环（收到 8px）挤成一坨。孤影/闪这种 ≤110px 的短路径上双线本来就分不开，
   全靠这两个环说「这是抓/突进」，环一塌就什么都读不出来。
   环半径本来就与路径长度无关，下限只是保住短路径那一档。
   断言：末段最小外环 ≥22px、两环间距 ≥12px、grab 的环数比 light 多一个。

## 4b. 悟时槽位已满 → 在悟的画面里选替换（决议 024）

**这一条挡的是一个零提示的死局。** 旧的 `Tech.learn` 只往空槽塞，塞不进去就什么都不做；
一周目到第五回四槽通常已满，于是无锋「学会了却装不上」，
而守阁人**只有无锋能撬开** —— Boss 完全无敌，游戏不给任何提示，
而 DESIGN §0 铁律 3 又不许弹教程。这是全游戏唯一「不换招就打不过」的 Boss。

做法：**有空槽时行为一个字不变**；四槽全满时，「悟」的画面下方浮出四个格子，
←/→ 选替换掉哪一格（缺省最后一槽），J 确认，超时按缺省。
无一字提示，和生杀抉择同一种语言：**朱砂 = 会发生的那一边**。
被选中的格子换成朱砂框、格里那一招淡到 0.26（它就要被顶掉了），
格子上方一颗随呼吸脉动的朱砂点，并从招名那一列牵一条朱砂线下来 —— 「这一招，进这一格」。

两个实现上的判断：

1. **替换写在 `exit()` 里，不写在 update 的关闭分支。**
   `Game.pop` 与 `Game.setScene` 都会调 `exit`，所以无论是确认、超时，

写入走契约 007 §1 的 `SJ.Player.setSlot`，断言用正则钉死不许绕过它直接写 `Save.data.slots`。

## 5. 招式进度入存档（决议 016）

- `Save.defaults()` 加 `techProgress: {}`。
- **真源仍在 `Tech.progress`**；`Tech.gain()` / `Tech.learn()` 变化时调 `persist()` 写回并落盘。
- 读回挂在 **`Save.load()`** 里（`SJ.Tech.adoptProgress(d.techProgress)`）。
  这样零外部改动 —— `level.js` / `menus.js` 都不用碰。
  守卫 `if (SJ.Tech && SJ.Tech.adoptProgress)` 是必需的：
  smoke / level-check / script-check 里 save.js 会在没有 tech.js 的情况下被加载。

三个坑，都验了：

1. **`Save.load()` 会换掉整个 `data` 对象**，所以 Tech 不许缓存 `data.techProgress` 的引用，
   `persist()` 每次现取 `SJ.Save.data`。和 player.js 把 `known/slots` 做成取值器是同一个坑。
2. **`adoptProgress` 是拷贝不是别名**。别名的话 `resetProgress()` 里的 `Tech.progress = {}`
   会让两边悄悄指到不同对象上，之后写的进度全是孤儿。
3. **`resetProgress()` 只在 `Save.exists()` 为真时才落盘**。
   决议 010 的「始」流程是 `Save.reset()` → `Tech.resetProgress()`；
   reset 刚把 localStorage 的键删掉，若 resetProgress 无条件 `save()`，
   就会凭空造出一个存档，**标题画面的「继」会亮起来**。这条也写成断言了。

存档里的 `techProgress` 被玩家手改坏（非数字 / 越界）不会抛：
非法值丢掉，越界值夹到 0–100。

## 6. 输入缓冲审计

工具：新建 `dev/input-audit.js`（`node dev/input-audit.js`）。
**为什么要单独一个脚本**：`SJ.Input.buffered()` 用的是 `Date.now()`（墙钟），
而 `player-check.js` 里 60 个固定步只花 1ms 真实时间，
所以在那边缓冲**永远不会过期**，任何与窗口长度有关的问题都测不出来。
这个脚本把 `Date` 换成受控时钟，每推进一个固定步就让墙钟走 16.67ms。

### 现状（实测，不是读代码猜的）

| 动作 | 缓冲 | 取消窗口 | 结论 |
|---|---|---|---|
| 跳 | `buffered('jump', 120ms)` | 落地前 **≤7 帧**按下都补跳，8 帧起不认 | ✅ 与 JBUF=7.2 帧完全吻合 |
| 土狼时间 | `COYOTE=0.10s` | 离地 5 帧内可跳、6 帧起不可 | ✅ 原有断言已覆盖 |
| 攻击 | `buffered('attack', 120ms)` | 见下 | ⚠️ 见「发现 1」 |
| 身法 | **无缓冲**（只 `pressed()`） | — | 冷却中按 L 不会在冷却结束时补冲 |
| 招式槽 t1–t4 | **无缓冲**（只 `pressed()`） | — | 硬直中按 U 不会在硬直结束时补放 |
| 可变跳高 | `released('jump')` | 见下 | ⚠️ 见「发现 2」 |

`consume()` 语义正确：按住不连发（按住 J 40 帧只出第一段）。
`lastPress` 随墙钟自然过期，**不存在「缓冲永不清」**。
`dropThrough` 也查过了，不是漏清：`world.js:72` 有 0.2s 的忽略窗口，由 World 自己维护。

### 已修 1（Lead 授权改 `src/core/input.js`，仅限时钟来源这一处）

**症状**：`Input.buffered` 数的是 `Date.now()`（墙钟），但 hitstop 期间游戏时间是停的、
墙钟照走。于是命中带来的定格把缓冲窗口白白烧掉：

```
修之前   挥空 1✗ 2✓ 3✓ …        命中(45ms) 1✗ 2✗ 3✗ 4✓ …
修之后   挥空 1✗ 2✗ 3✓ …        命中(45ms) 1✗ 2✗ 3✓ …   ← 两行完全一致
```

**你砍中了反而比砍空多吞掉 2 帧输入** —— 越打中越连不上，方向是反的。
45ms 是最轻一档；第二段 60ms、第三段 90ms、镇山 140ms 只会更明显。

**改法**：`now()` 从 `Date.now()` 换成 `(SJ.Game && SJ.Game.time || 0) * 1000`。
`Game.time` 单调递增、永不重置；hitstop（dt=0）时不前进（这正是要的）；
暂停/对话层照常前进（`game.js` 的 `step` 无条件 `G.time += dt`），所以缓冲不会穿过暂停菜单。

**连带必须改的一行**：`clearAll()`（失焦 / 切标签页）现在还要清 `lastPress`。
改用游戏时间之后，切走标签页 → rAF 停摆 → 游戏时间冻结 → 按下去的键会**原样等在那里**，
切回来当帧兑现。墙钟时代它会自己过期，所以以前不需要这一行。已在审计里验了。

**换时钟带来的一帧偏移，已按 Lead 批准补回**：
换成游戏时间之后，`G.time` 在 `step()` 里**先自增再跑 update**，
而 `lastPress` 是上一帧末尾的 DOM 事件记的，于是测出来的间隔天然多含当前这一帧 ——
**120ms 的窗口实际只剩 6.2 帧可用**（原来在墙钟下是 7.2 帧）。
所以 `player.js` 顶部把两个缓冲常量各 +1 帧：

```js
var FRAME = 1 / 60;
var JBUF = 0.12 + FRAME;   // 跳跃缓冲，有效 7.2 帧
var ABUF = 0.12 + FRAME;   // 攻击缓冲（原来两处调用点写死 120）
```

这是**保住原行为**，不是调数值：改之前 120ms 就等于 7.2 帧可用。
`dev/input-audit.js` 把改造前的挥空那一行写成了字面量基线，
命中与挥空**都必须等于它**，两种回归各自会亮：
两行不一致 = 缓冲又在数墙钟；两行一致但整体右移 = 有效帧数被时钟换算吃掉了。

```
最终   挥空 1✗ 2✓ 3✓ …   命中 1✗ 2✓ 3✓ …   跳跃缓冲 落地前 ≤7 帧 ✓、8 帧起 ✗
```

顺带纠正我自己一句：我原来那套墙钟探针（keydown 之后才推进 FAKE_MS）是**偏乐观**的，
真实浏览器落在两者之间；游戏时间这套是精确的。所以「挥空 2✓」这个基线本身略微理想化，
但既然它就是改造前玩家实际拿到的手感，用它当基线是对的。

**没动的一处**：`src/main.js:35` 那个独立的兜底玩家也写着 `I.buffered('jump', 120)`，
它有自己的一套物理、不走 player.js，所以同样会少一帧。那是 Lead 的文件，只报告。

### 已修 2（player.js，Lead 批准）—— 松手那帧落在受击/招式里，可变跳高会丢

可变跳高的截断（`released('jump') && vy < JUMP_SHORT`）原来只写在 `control()` 里，
而 `control()` 在 `hurt` / `dash` / `cast` 分支根本不跑，那一帧的 `released` 边沿
当帧就被 `Input.update()` 清掉，永久丢失。实测顶点：

```

正常点按           52.3px   52.3px   ← 没有回归
松手那帧在受击中   114.0px    52.3px   ← 修好了（原来变成长按跳的高度）
松手那帧在身法中    12.0px    12.0px   ← 这个不是 bug：身法本来就把 vy 清零
```

抽出 `jumpCut(p)`，在 `hurt` 与 `cast` 两条早退分支里补调。
**位置很讲究**：必须在同一帧的**起跳之后**。放在 `tick()` 开头的话，
同帧按下并松开时截断会先于起跳执行，短跳就永远截不到了——
既有断言「点按跳顶点 52.33」会立刻变成 114 而不报别的错。

| 招式槽 t1–t4 | **无缓冲**（只 `pressed()`） | 硬直中按 U 不会在硬直结束时补放 |
