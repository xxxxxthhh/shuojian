# REVIEW —— 第一版实现的评审与增强计划（2026-09-07）

> 本文件含全部玩法剧透，供增强波次的 teammates 阅读。玩家请勿打开。
> 评审者：Lead。证据来源：8 关巡逻机器人实测、四套自检、七份 notes-*.md 自报、玩家（用户）前两回的真实反馈。

## 0. 现状一句话

游戏**能从头跑到尾**（188 节点、8 关、12 招、7 敌 6 boss、~11.4k 行、四套自检全绿），
但**真人只玩过前两回，机器人只能自动通过前两回**——第三到第七回从来没有任何一次「有人/有机器人从头走到尾」的记录。
用户在 20 分钟游玩里撞了两次软锁（序章硬墙、客栈跨层触发）。这就是当前最大的风险：不是玩法不够，是**后六回没人验证过**。

## 1. 实测证据

### 1.1 八关巡逻机器人（dev/walk.js，每关上限 720s）
| 关 | 结果 | 说明 |
|---|---|---|

| c2 客栈 | ✗ 卡 x=375 | **机器人问题**：需从 x=340 跳上 (470,700) 单向台阶越过水池，机器人直接走进水里→重生→循环 |
| c3 长河 | ✗ 卡 x=379 | **机器人问题**：地面到 720 结束，需跳上 (840,560) 石柱；落水重生点在 379 |
| c4 雪山 | ✗ 卡 x=572 | **机器人问题**：顶风（windAx=-600）爬 60px 台阶，位置来回晃，「连续不动」检测永远不触发 |
| c5 藏经阁 | ✗ 卡 x=3674 | **机器人问题**：顶着 x=3700 的 blocker（c5_page 标志）原地跳了 12 分钟；标志由 levels.js:753 的触发器设，机器人不会去触发 |
| c6 城楼 | ✗ 720s 超时 x=4147 | **机器人太弱**：第 5 波 3 个敌人还活着，机器人打得慢（c1 四波就用了 444s） |
| f 终章 | ✗ 卡 x=3248 / exitX=3260 | **疑似机器人判定问题**：p.x+w/2 已过 exitX，多半是结局链已播完、菜单被机器人按掉、关卡场景还在更新；机器人只认「关卡序号变化」。**T1 须明确验证结局流程**（Menu.ending 是否被推入） |

结论：**自动化覆盖在第二回开始就归零**。机器人只会「同层平推 + 卡住就跳」，不会过水、不会等筏、不会顶风。
这不是机器人的锅——是我们没有一个能通关的机器人，就等于没有回归测试。

## 2. 提升意见（按玩家影响排序）

### P0 可靠性：让后六回「被走过」
1. **能通关的机器人**：在 solids 上做 BFS/跳跃规划（跳高 114、跳远按 vx 算），会：过水（找落脚点）、等筏、顶风补偿、上升气流、blocker 交互、对话推进、看预警格挡、boss 阶段策略。目标：**8 关全部自动通关**，每关输出真实秒数。
2. **软锁扫荡**：机器人通关过程中每一次「门锁着但无可达敌人」「busy 卡住」「敌人掉出世界」都自动分类（walk.js 已加判定行）。每发现一类 → level-check 加一条规则（现有 17 条，这套模式已证明有效）。
3. **时长实测 vs 预算**：c1 机器人 444s / 预算 245s 说明「预算」是拍的。8 关跑完得到真实表，若总时长 < 30 min，**按密度加而不是加走廊**（c5 已经 33 屏了）。
4. **跨层/跨门的运行时规则**再审：rescueFoes 把敌人传到玩家身边会不会把 boss 传进墙；onSameFloor 的 130px 容差对 c2 三层（220px 间距）够，对别的关未验证。

### P1 手感：打击层次 + 招式辨识
5. **12 招各自的起手式与命中姿势**：至少每招一个独特 silhouette（figure.js 加 pose，tech.js 引用），不再共用 castWind/castHit。
6. **atk1/atk2/atk3 剪影分离**：横/竖/斜三个方向感。
7. **命中确认分层**：轻击 / 重击 / 完美格挡 / 处决 四档不同的 hitstop、震幅、墨点数、音量。现在的差别靠数值微调，没有「档」的概念。
8. **招式进度入存档**：save 加 `techProgress` 字段（需决议：schema 加字段、默认 `{}`，旧档兼容）。

### P1 敌人：可读性
9. **预警分层**：可格挡=墨线，不可格挡（superArmor 大招）=朱砂线，抓/突进=双线。玩家能在 0.3s 内决定挡还是闪。
10. **Boss 阶段转换演出**：现在 phases 只是数值切换；给一个 0.6s 的「换势」停顿 + 墨迹变化，让玩家知道规则变了。
11. **公平性审计**：用机器人的命中/格挡数据看每个 boss 的招是否有 ≥ 0.25s 的反应窗口。

### P2 呈现：一关一景
12. 八关背景现在同质（山 / 竹 / 雨的排列组合）。每关一个独有的构图主体：茶馆的檐与灯、竹林的疏密节奏、客栈三层的梁柱透视、长河的倒影与岸线、雪山的天空洗色与留白、藏经阁的火光与飞灰、城楼的月与旗、终章的空。
13. `Ink.water` 加倒影 + 岸线；竹子按泊松分布而不是等距；`Ink.splat` 去对称。
14. c4 雾、c5 火、c6 月/旗 —— 天气不只是粒子，要影响调色。

### P2 系统
15. 音量滑条替代静音开关（menus.js + audio.js 暴露 setVolume）。
16. 叙述面板 / c5_book 九屏节奏：加「第 n/9 页」的位置感，让玩家知道还有多久。

### 不在本波做的
- **音频合成**：没人能听。用户没抱怨；改了也是盲改。等用户说「哪里不对」再定向修。
- **玩法/数值/存档结构**（除第 8 条）：用户正在探索期，任何玩法改动都会打断他的发现过程。本波只做**打磨与可靠性**。
- 手柄、按键重映射：没人要。

### 4.5 本波的过程教训（写给下一个 Lead）
- 决议必须先核现状再写（014 的「墨线」、019 的 0.6s 都是拍脑袋，被 teammate 纠正）。
- 消息会交叉：teammate 按旧版决议做完再改，两次。裁定一律落 CONTRACTS.md，消息只是通知。
- Lead 提交只列显式路径，绝不 `-a/-A`（三次卷进半成品，重写历史修复）。
- 共用目录禁通配符删除（T4 事故）。
- 无头验证三个假象：推过头粒子已回收 = 「管道不通」；后台 rAF 节流 = 「永远第一帧」；`getImageData` 每帧统计污染 fps。结论只认坐标与断言，不数像素。
- 数字达标 ≠ 好看：T4 第一版留白/帧耗时全达标，画面是 CAD。成图必须有人看。
