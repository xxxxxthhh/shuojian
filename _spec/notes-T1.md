## 2. 机器人怎么做的

三层，外加一条铁律：**输入模型必须是真的**。

1. **输入层**（`harness.js`）。walk.js 那套替身把 `down/pressed/buffered` 都接成「held || edge」，
   于是 `buffered('jump')` 恒真，玩家一落地就再跳一次 —— 第一回跳了 967 次。
   这里改成如实复刻 `src/core/input.js`，唯一的改动是把它的墙钟换成**虚拟帧钟**
   （无头跑得比实时快几百倍，120ms 的跳跃缓冲窗口会覆盖上百帧）。
   `Math.random` 用 mulberry32 定种子，否则敌人 AI 每次不同，时长表就是噪声。

2. **导航层**（`nav.js`）。每 8 帧从**活的** `SJ.World.solids` 建表面图（浮筏按整段行程建面，
   执行时用它此刻的实际位置），边分 walk / jump / jump2 / fall / fall2 / updraft，Dijkstra 求路。
   跳跃包络不用纸上公式，用 `jumpcal.js` 在真沙盒里量出来的：

   | | 高 | 远 |
   |---|---|---|
   | 满跳（助跑满速） | **114.0px** | **152.0px** |
   | 二段跳（顶点补第二跳） | **204.7px** | 228px（模型 240，差 5%） |
   | 顶风（第四回 windAx=−600）满跳向右 | 114.0px | **79.3px** |
   | 顶风走路稳态 | — | vx 240 + envVx −115 = **125px/s** |
   | 风口（第四回）静止不动 | 只被托 **108px** | —— 够不到 620px 的崖顶 |

   最后一行是设计意图容易被误读的地方：风口**不是电梯**。`envVy` 稳态只有 −800px/s，
   而 `p.vy` 会一直累加重力，净速度约 0.33s 后就归零。真正过崖的走法是**站进风口反复起跳**
   （每次落回崖底平台都把二段跳还回来）——机器人就是这么过的。

   模型与实测逐项对齐（`node dev/jumpcal.js` 是一条会红的自检）。

3. **执行层**（`autoplay.js`）。目标优先级：Boss → 被锁的波次 → blocker 的 setter trigger →
   bossScript.pre 的 trigger → exitX。移动按路线的「下一块面」反应式驱动，战斗见 §6。

### 通关判据：终章走的是 `setScene`，不是 `push`（实证）

REVIEW §1.1 里终章那条「✗ 卡 x=3248 / exitX=3260」**不是软锁，是判定问题** —— 已实证：

```
SJ.Level.complete()  → idx 是最后一关 → SJ.Story.ending()
SJ.Story.ending()    → runChain('f_end')          ← push，栈 = [关卡, 对白]
                     → 链播完 → SJ.Menu.ending(kind)
SJ.Menu.ending()     → SJ.Game.setScene(endingScene)   ← ★ setScene 会清空整个栈
```

所以通关那一刻 `SJ.Game.stack` 变成**长度 1、且 `stack[0]` 不再是关卡场景**。
只认「`SJ.Level.current` 变了」的机器人永远等不到那个变化 —— 关卡序号是最后一关，不会再加一。
`harness.js` 的判据是：载入时记下 `levelScene = SJ.Game.stack[0]`，之后

```js
if (stack[0] !== levelScene) return 'ending';   // 关卡场景被整个换掉
if (stack.length === 1)      return 'level';
return 'overlay';                                // 对白 / 生杀抉择 / 暂停 / 死亡
```

三条结局分支（全饶 / 全杀 / 混合 mercy 表）都验过，都能走到 `Menu.ending`。
**以后所有机器人的通关判据都应该用这条，不要用关卡序号。**

### 三个只有跑起来才会发现的坑（都已在代码里写了注释）

- **跳跃键要留松开的帧**。第一版 `jumpTimer` 归零那一帧 `want.jump` 还是 1，紧接着又填满 →
  跳跃键一辈子按着，只有开局那一次按下沿。表现是「顶着 60px 的石台原地跑」，不报任何错。
- **空中不许改主意**。`surfaceUnder` 在腾空时会返回「正下方那一块」，于是人还在半空掠过下一块台子时，
  规划器以为已经站上去了，改planning下一跳、判定会落短、当场补二段跳 → 弹起 200px 飞过目标掉进河里。
  改成起跳那一刻锁定目标面，落地才解锁。
- **攻击会把跳跃整个吃掉**。`player.js` 的 `control()` 在攻击状态里直接 `return`。
  机器人把「站在 60px 台子上的敌人」判成够得着 → 一直挥空刀 → 按了跳也不离地。
  第四回第一波实测卡九百秒，日志里 `st` 永远是 atk1/atk2/atk3。改成按脚底高差 44px 判「够得着」。

### 3.3 对真人的估算 —— 结论：**不加波次**

机器人几乎不看字：它每 6 帧点一次 confirm，184 屏总共只花约 37s。
`level-check.js` 自己按 **3.4s/屏** 算的剧情时间是 **626s**。所以

```
真人 ≈ 机器人 2416s − 机器人的对白 37s + 真人的对白 626s ≈ 3005s ≈ 50.1 min   （饶 seed23）
真人 ≈ 机器人 1324s − 37s + 626s                        ≈ 1913s ≈ 31.9 min   （杀 seed3）
```

两个种子差得很远，差的**全在第六回**（1615s vs 355s）。取更保守的那一头：**31.9 min**，
仍然越过 DESIGN §9.6 的 30 分钟线；而这是**下界**，三条都往上走：

- 机器人的完美观势率高得不像人（第六回一场 206 次完美格挡）；真人会挨更多打、死更多次，每死一次要从检查点重打。
- 机器人不会迷路：它有全图表面图，真人要找路（第五回 33 屏、第二回三层）。
- 机器人不看风景、不试招、不换招、不读题壁。

**结论：不需要加波次，`src/data/levels.js` 的波次/几何一行未改**（只加了决议 012 的 `only` 字段）。

## 4. 软锁扫荡

### 4.1 真软锁 #1（已修）：第二回第 5 波 —— 敌人走出战场楼层

- **现象**：`gate=[1400,3400]`、一个力士活着、玩家在三层，四百秒过去还在等一个够不到的人。不报任何错。
- **原因**：三层地板从 x=1400 起，gate 也从 1400 起。玩家被 `clampPlayer` 夹在 x≥1400 出不去，
  **敌人不受 gate 约束** —— 力士从三层左沿走下二层，站在 gate 区间里但矮一整层（220px），
  `onSameFloor` 判它不同层，波次永远清不掉。
- **实测证据**：`f23999 敌 lishi 脚底 y=600 x=1677（本波楼层 380）玩家 x=3579 脚底=380 gate=[1400,3400]`
- **修法**（`rescueFoes`）：活跃波次的敌人夹回 `R.gate`；**掉到本波楼层之下超过一层楼**的按回本波楼层
  （`putBackOn` 会去找那一层真的有地面的一段，不是硬写 `e.y`）。Boss 同理夹回 `bossArena` / `bossY`。
- **只捞掉下去的，不动站高处的**：第二、四、六回都故意把弓手放在比战场高一层的挑台上
  （「弓手在挑台上：第一次退无可退，答案是爬上去」）。双向判定会把他每帧拽下来 —— 那是改玩法。

### 4.2 真软锁 #2（已修）：第二回的检查点跨层错拿

- **现象**：死亡审计里发现第二回第 2–5 波的复活点全是 `cp#3 @1450,380` —— 那是**三层**。
- **原因**：`updateCheckpoints` 只比 x。而 checkpoints 是按**推进顺序**写的，不是按 x 排的：
  `[[100,760],[2100,820],[1500,600],[1450,380]]`（三层客栈，先右、再上、再往回走）。
  玩家在**一层**走过 x=1450（第 1 波的 gate 右界是 1500，必然会走到）就把检查点设成三层的那个，
  而 `cp` 只增不减、再也回不去。
- **后果**：之后在一层任何地方死一次，直接复活到三层 —— 第 2、3、4 波连同它们的剧情与教学整段被跳过，
  玩家还以为自己打过了。不报错，也没人会发现。
- **实测**：`玩家在一层 x=1470 y脚底=820 → flags.cp = 3 → 复活点 [1450,380]`
- **修法**（与波次的 `onSameFloor` 同源）：到达检查点要求 x 到了**且**脚底真的在那一层。
  修后：一层 x=1470 → cp0；一层 x=2110 → cp1；三层 x=1460 → cp3。复活审计里第二回的序列也跟着对了。

### 4.3 决议 022（已实现）：死亡复活满血 / 进新章满血

- **原状**：`Player.create` 读 `Save.data.hp`，而那个字段只在 `complete()` 里写过一次。
- **实测（修之前，seed=7 连续周目）**：
  ```
  出第1关: 通关时 hp=2 → 存进 data.hp
  进第2关: 场上 hp=2   本关每次死后都复活成 2 血 → 死 16 次 / 417s
  进第3关: 场上 hp=2   → 死 54 次 / 900s 没打完
  ```
  只要有一关残血通关，后面整局锁死在那个血量上，而游戏没有任何回血手段。
- **实现**：`restartFromCheckpoint` 载入前 `d.hp = d.maxHp`；`complete()` 写 `d.hp = d.maxHp`。
  `player.js` / `save.js` 一行没碰。
- **验证**：`respawn-audit` 每一波都断言 `hp === maxHp`；两条分支的连续周目**去掉旁路开关后跑通**（§3.1）。

### 4.4 决议 023（已实现）：无门波次不阻塞后面的波

- **原状**：`updateWaves` 里 `if (R.active) { …; return; }` 无条件挡住后面所有波。
  没有 gate 的波玩家本来就跑得掉 —— 留一个活口，后面所有波次永远不刷。
- **实测（修之前）**：第五回第 2 波的僧人被打到 1 血就被丢下，第 3 波（Boss 前那三个）整场再没出现过。
- **实现**：无 gate 的活跃波次，玩家走到后一波的触发区（且同层）时视为结束，
  `cleared = true`（`afterWave:` 条件照常成立），敌人留在原地当散兵、不再计入门锁。有 gate 的语义不变。
- **验证**：规则 22 用 harness 真跑一遍；把 023 的分支关掉，规则立刻变红（验过）。
  复活审计里第五回 wave3 也从「⚠ 打不出来」变成了 ✓。

### 4.5 决议 012（已接线）：教具刀客的 `only`

`level.js` 的 `spawnWave` 从来只传 `{facing:-1}`，`opts.only`（ai.js:166）一直没人调 ——
决议 012 路径三的教具「第一回第一个刀客只出破雨」**从来没生效过**，他一直在随机出招。
现在 `levels.js` 的那条 spawn 带 `only: ['poyu']`，`spawnWave` 透传。
实测：`第一回第一波刀客 only = ["poyu"]`。规则 23 守住它。

### 4.6 顺手修掉的隐患：`rescueFoes` 会把 Boss 捞到屋顶上

原来捞掉出世界的敌人用 `SJ.World.groundAt(e.cx(), 0)`。`yFrom=0` 的语义是「从天上往下找第一块地」，
在第二/五/六回这种多层关卡里那是**屋顶**。Boss 被捞到屋顶，玩家在 `bossArena` 里永远打不到他 —— 同一类死局。
现在从 `bossY` / 本波楼层往下找。（这条是静态推理 + 代码阅读得出的，**没有实测复现过 Boss 掉出世界**，见 §8。）

### 4.7 新增 checker 规则（每条都有变异测试或真跑验证）

### 4.8 变异测试逼出的既有规则漏报：规则 14 会穿天花板

`node dev/level-check-mutate.js` 把「拆掉第二回通往三层的最后一级台阶」当成变异，
**规则 14 原来照样全绿** —— 它的 `link()` 只看高差与水平间距，于是认为
「站在 1800 那根柱子顶上可以跳到正头顶那层楼板」，而那层楼板在柱子上方是**天花板**。
（我的规划器踩的是同一个坑，第二回卡了三百秒。）已给 `link()` 补上起跳点头顶净空判定：
往上跳时，实心目标要求起跳点在目标水平范围之外，单向平台可以从下面穿上去，两者都要过净空。
现在这条变异会红。

### 4.9 `onSameFloor` 的 130px 容差 —— 逐关验过

对每一关每一波，列出「触发区内、离本波楼层 130px 以内的其它可站立面」：

## 5. 死亡复活审计

真正的难点是别的：

- **第六回师兄是全游戏最陡的墙**。连续周目里两个种子分别是 355s / 3 死 和 **1615s / 22 死 / 挨打 125 次**，
  方差比任何一关都大；单关 5 个种子只有 1 个在 900s 内打完。相比之下 c1–c5 的 Boss 都是 38–160s、0–1 死。
- **第五回守阁人 290s** 不是难，是**长**：他不出伤害（机器人全场 0 次挨打），
  时间全花在「读势 → 学无锋 → 用无锋撬开 2.6s → 输出」的循环上。

### `windMul` 的判据（Lead 要的）

§3.1 那张表的「受击次数 / 伤害」列就是判据。一周目里前五回的受击都在 **3–5 次 / 23–50 伤**这个带子里，
彼此差别很小；只有第六回是 **22–125 次 / 239–1374 伤**，高出一个数量级。

**读法：难度曲线的问题不在「二到六回该不该整体调倍率」，而在第六回单点。**
按章节倍率整体调（一回 1.15 / 六回 0.62）会把已经很平的前五回也动了，
而真正需要动的只有师兄那一场。我的建议是**不要开 `windMul` 这个旋钮**，
要动就动师兄（血量 520 / 三阶段 / 复制招式，对上 60 血的主角）。判断权在你和 T3。

### 观势的性价比高得离谱（T3 调 Boss 时值得知道）

完美观势 = 全额免伤 + 回墨 18 + 敌人硬直 0.9s，而观势在墨 ≤20 时**不再扣墨**（`INK_FLOOR`）。
我在第六回 Boss 上扫过参数：

| 机器人策略 | 完美观势 | 挨打 | 死 |
|---|---|---|---|
| 只在起手式过了三成后才举手（200px 内） | 60 | 249 | 43 |
| 起手式一出现就举手（260px 内） | 110 | 199 | 33 |
| **贴身 140px 内一直举手** | 42 | **24** | **3** |

也就是说：**一个只会「贴脸一直按住 K」的玩法，能把第六回 Boss 的挨打次数压到十分之一。**
如果这不是设计意图，可能需要给观势加个代价（这是玩法改动，我没动）。
