## 2. 机器人怎么做的

三层，外加一条铁律：**输入模型必须是真的**。

1. **输入层**（`harness.js`）。walk.js 那套替身把 `down/pressed/buffered` 都接成「held || edge」，
   于是 `buffered('jump')` 恒真，玩家一落地就再跳一次 —— 第一回跳了 967 次。
   这里改成如实复刻 `src/core/input.js`，唯一的改动是把它的墙钟换成**虚拟帧钟**
   （无头跑得比实时快几百倍，120ms 的跳跃缓冲窗口会覆盖上百帧）。
   `Math.random` 用 mulberry32 定种子，否则敌人 AI 每次不同，时长表就是噪声。

2. **导航层**（`nav.js`）。每 8 帧从**活的** `SJ.World.solids` 建表面图（浮筏按整段行程建面，
   执行时用它此刻的实际位置），边分 walk / jump / jump2 / fall / fall2 / updraft，Dijkstra 求路。
   跳跃包络不用纸上公式，用 `jumpcal.js` 在真沙盒里量出来的：

   | | 高 | 远 |
   |---|---|---|
   | 满跳（助跑满速） | **114.0px** | **152.0px** |
   | 二段跳（顶点补第二跳） | **204.7px** | 228px（模型 240，差 5%） |
   | 顶风（第四回 windAx=-600）满跳向右 | 114.0px | **79.3px** |
   | 顶风走路稳态 | — | vx 240 + envVx −115 = **125px/s** |

   模型与实测逐项对齐（`node dev/jumpcal.js` 是一条会红的自检）。

3. **执行层**（`autoplay.js`）。目标优先级：Boss → 被锁的波次 → blocker 的 setter trigger →
   bossScript.pre 的 trigger → exitX。移动按路线的「下一块面」反应式驱动（顶墙/临边/需要爬高就起跳，
   过顶点预判落点不够就补二段跳），战斗见 §6。

### 三个只有跑起来才会发现的坑（都已在代码里写了注释）

- **跳跃键要留松开的帧**。第一版 `jumpTimer` 归零那一帧 `want.jump` 还是 1，紧接着又填满 →
  跳跃键一辈子按着，只有开局那一次按下沿。表现是「顶着 60px 的石台原地跑」，不报任何错。
- **空中不许改主意**。`surfaceUnder` 在腾空时会返回「正下方那一块」，于是人还在半空掠过下一块台子时，
  规划器以为已经站上去了，改planning下一跳、判定会落短、当场补二段跳 → 弹起 200px 飞过目标掉进河里。
  改成起跳那一刻锁定目标面，落地才解锁。
- **攻击会把跳跃整个吃掉**。`player.js` 的 `control()` 在攻击状态里直接 `return`。
  机器人把「站在 60px 台子上的敌人」判成够得着 → 一直挥空刀 → 按了跳也不离地。
  第四回第一波实测卡九百秒，日志里 `st` 永远是 atk1/atk2/atk3。改成按脚底高差 44px 判「够得着」。

### 3.3 对真人的估算 —— 结论：**不加波次**

机器人几乎不看字：它每 6 帧点一次 confirm，184 屏总共只花约 37s。
`level-check.js` 自己按 **3.4s/屏** 算的剧情时间是 **626s**。所以

```
真人 ≈ 机器人 1745s − 机器人的对白 37s + 真人的对白 626s ≈ 2334s ≈ 38.9 min   （饶）
真人 ≈ 机器人 2134s − 37s + 626s                        ≈ 2723s ≈ 45.4 min   （杀）
```

而这还是**下界**，三条都往上走：
- 机器人的完美观势率高得不像人（第六回 Boss 一场 19 次完美格挡、只挨 9 下）；真人会挨更多打、死更多次，每死一次要从检查点重打。
- 机器人不会迷路：它有全图表面图，真人要找路（第五回 33 屏、第二回三层）。
- 机器人不看风景、不试招、不换招、不读题壁。

**38.9 min 已明显越过 DESIGN §9.6 的 30 分钟线，且余量来自最不可能高估的那一侧。
按 REVIEW §2.3 的判据，不需要加波次，`src/data/levels.js` 保持原样（本波一行未改）。**

需要说明的两处偏差：
- **第六回**预算 410s，机器人要 912–1364s。那不是关卡太长，是**机器人打不过师兄**（见 §6），不能当关卡时长用。
- **第一、三回**机器人明显快于预算（95s / 106–216s vs 245s / 330s），因为机器人的战斗效率远高于人（见上）。
  剧情屏数补上之后（c1 有 21 屏 = 71s）差距就小得多。

## 4. 软锁扫荡

### 4.1 真软锁 #1（已修）：第二回第 5 波 —— 敌人走出战场楼层

- **现象**：`gate=[1400,3400]`、一个力士活着、玩家在三层，四百秒过去还在等一个够不到的人。不报任何错。
- **原因**：三层地板从 x=1400 起，gate 也从 1400 起。玩家被 `clampPlayer` 夹在 x≥1400 出不去，
  **敌人不受 gate 约束** —— 力士从三层左沿走下二层，站在 gate 区间里但矮一整层（220px），
  `onSameFloor` 判它不同层，波次永远清不掉。
- **实测证据**：`f23999 敌 lishi 脚底 y=600 x=1677（本波楼层 380）玩家 x=3579 脚底=380 gate=[1400,3400]`
- **修法**（`src/level/level.js` `rescueFoes`，纯运行时健壮性，不动关卡数据）：
  活跃波次的敌人夹回 `R.gate`；**掉到本波楼层之下超过一层楼**的按回本波楼层
  （`putBackOn` 会去找那一层真的有地面的一段，不是硬写 `e.y`）。Boss 同理夹回 `bossArena` / `bossY`。
- **只捞掉下去的，不动站高处的**：第二、四、六回都故意把弓手放在比战场高一层的挑台上
  （「弓手在挑台上：第一次退无可退，答案是爬上去」）。双向判定会把他每帧拽下来 —— 那是改玩法。

### 4.2 真软锁 #2（已修）：第二回的检查点跨层错拿

- **现象**：死亡审计里发现，第二回第 2–5 波的复活点全是 `cp#3 @1450,380` —— 那是**三层**。
- **原因**：`updateCheckpoints` 只比 x。而 checkpoints 是按**推进顺序**写的，不是按 x 排的：
  `[[100,760],[2100,820],[1500,600],[1450,380]]`（三层客栈，先右、再上、再往回走）。
  玩家在**一层**走过 x=1450（第 1 波的 gate 右界是 1500，必然会走到）就把检查点设成三层的那个，
  而 `cp` 只增不减、再也回不去。
- **后果**：之后在一层任何地方死一次，直接复活到三层 —— 第 2、3、4 波连同它们的剧情与教学整段被跳过，
  玩家还以为自己打过了。不报错，也没人会发现。
- **实测**：`玩家在一层 x=1470 y脚底=820 → flags.cp = 3 → 复活点 [1450,380]`
- **修法**（`src/level/level.js`，与波次的 `onSameFloor` 同源）：到达检查点要求 x 到了**且**脚底真的在那一层。
  修后：一层 x=1470 → cp0；一层 x=2110 → cp1；三层 x=1460 → cp3。
- **配套规则 21**：同一层上的检查点必须按 x 递增（变异：把第二回三层那个检查点压到一层高度 → 规则红）。

### 4.3 顺手修掉的隐患：`rescueFoes` 会把 Boss 捞到屋顶上

原来捞掉出世界的敌人用 `SJ.World.groundAt(e.cx(), 0)`。`yFrom=0` 的语义是「从天上往下找第一块地」，
在第二/五/六回这种多层关卡里那是**屋顶**。Boss 被捞到屋顶，玩家在 `bossArena` 里永远打不到他 —— 同一类死局。
现在从 `bossY` / 本波楼层往下找。（这条是静态推理 + 代码阅读得出的，**没有实测复现过 Boss 掉出世界**，见 §8。）

### 4.4 新增 checker 规则（每条都有变异测试）

| 规则 | 断言 | 变异（故意改坏数据后必须红） |
|---|---|---|
| **18** | 带 gate 的波，本波楼层在 gate 区间内地面连续 | 第二回三层地板从 gate 中间断开 / 第六回 gate 拉到地面尽头之外 |
| **19** | Boss 场地在 bossY 那一层地面连续 | 第一回 Boss 场地地面砍掉一半 / 第五回 bossY 抬高一层 |

### 4.5 变异测试逼出的既有规则漏报：规则 14 会穿天花板

`node dev/level-check-mutate.js` 把「拆掉第二回通往三层的最后一级台阶」当成变异，
**规则 14 原来照样全绿** —— 它的 `link()` 只看高差与水平间距，于是认为
「站在 1800 那根柱子顶上可以跳到正头顶那层楼板」，而那层楼板在柱子上方是**天花板**。
（我的规划器踩的是同一个坑，第二回卡了三百秒。）已给 `link()` 补上起跳点头顶净空判定：
往上跳时，实心目标要求起跳点在目标水平范围之外，单向平台可以从下面穿上去，两者都要过净空。
现在这条变异会红。

### 4.6 `onSameFloor` 的 130px 容差 —— 逐关验过

对每一关每一波，列出「触发区内、离本波楼层 130px 以内的其它可站立面」：

| 关 | 结果 |
|---|---|
| c2（三层客栈，层间距 **220**） | 五波全部 ✓ 只有本层能触发 —— 130 把三层干净分开 |
| c1 | w1–w4 有 60/110px 的垫脚石在容差内。**这是对的**：那是同一层地面上的小台子，从上面触发这一波完全合理 |
| c4 | w1 有 60px 的梯田台阶在容差内。同上，那是缓坡不是楼层 |
| c5 | w2 有 60px 的相邻台阶在容差内。同上 |
| c6 | w2 有 120px 的单向挑台在容差内。从挑台触发再跳下来即可，无害 |
| c3 / f / p | 触发区内没有第二层 |

**结论：八关里没有任何一处「真正的另一层楼」落在 130px 之内**（最小的真层间距是 c2 的 220，
c6 的 160 是挑台不是楼层）。130 这个数目前既不误伤也不漏判。
⚠ 这个 130 在 `src/level/level.js` 的 `FLOOR_TOL` 和 `dev/level-check.js`（规则 17/18/20）里各有一份副本，
改一处要改两处 —— 两边都写了注释。

## 5. 死亡复活审计

`node dev/respawn-audit.js`，两段：

- **A 静态**：八关 × 每个检查点 → 复活点是否埋在实心块里 / 脚下有没有地面 / 在不在水火里 / 在不在未开的 blocker 之后 / 出不出界。
- **B 动态**：每一关每一波 → 让机器人打到那一波，**当场 `p.hurt(9999, null, {forced:true})` 打死**，
  点掉死亡界面，然后检查：复活点合理、`gate` 已解开、`activeWave` 已清、场上没有旧敌人残留、
  `busy` 不为真、已开的 blocker 没有被关回去，**并把关卡交回机器人真的跑到通关**。

只查「复活后 3 秒有没有位移」是不够的：那证明不了后面走得通。
例如第五回若检查点在 `fireStart` 之后，复活时 `R.fireT` 回到 −1，火再也不会起 ——
只有真的跑完才看得出还能不能通关。

### 5.1 结果（`node dev/respawn-audit.js`）

- **A 静态：八关所有检查点全部合格** —— 没有埋在墙里的、没有悬空的、没有落在水火里的、没有出界的。
- **B 动态：22 个波次里 19 个验过「死一次之后还能跑完这一关」**。复活点全部落在正确的检查点上，
  `gate` 已解开、`activeWave` 已清、场上没有旧敌人残留、已开的 blocker 没被关回去。
  第二回的检查点序列现在也对了（cp#0 → cp#2 → cp#3，不再一上来就跳三层）：
  ```
  ✓ [2 c2] wave2 复活后能跑完：复活点 87,706   (cp#0 @100,760)，再用 146s 通关
  ✓ [2 c2] wave4 复活后能跑完：复活点 1487,546 (cp#2 @1500,600)，再用 56s 通关
  ✓ [2 c2] wave5 复活后能跑完：复活点 1437,326 (cp#3 @1450,380)，再用 60s 通关
  ```
- **3 个失败全在第六回**（wave1/3/4），分类都是「机器人问题：同层敌人没打完」—— 600s 打不完师兄，
  不是软锁（见 §8.1）。
- **1 个提醒**：第五回 wave3 机器人根本没能把它打出来 —— 那是 §9.3 那个「一次只跑一波」的问题，不是复活的问题。

⚠ 这一段的第一版是**假绿**：`gameoverScene` 是先 `Game.pop()` 再 `Level.restartFromCheckpoint()`，
中间有一帧栈已经回到关卡层但重载还没发生。在那一帧取样，查到的全是重生**之前**的状态。
现在改成等 `SJ.player` 换成新对象才算重生完成 —— 第二回的检查点 bug（§4.6）就是修完这个才浮出来的。

- **第六回师兄是全游戏最陡的墙**。机器人单关 5 个种子只有 1 个在 900s 内打完，死 12–14 次；

## 9. 报给 Lead 的三件事（都不是我的文件 / 都涉及玩法，未擅自改）

### 9.1 死后从检查点复活，血量用的是「上一关通关时」的血 —— 需要裁定

`SJ.Save.data.hp` 只在 `Level.complete()` 里写一次，`Player.create` 读它；检查点存档不更新 hp。
实测（seed=7 连续周目，未开 `--fullhp`）：

```
出第1关: 通关时 hp=2 → 存进 data.hp
进第2关: 场上 hp=2   本关每次死后都复活成 2 血 → 死 16 次 / 417s
进第3关: 场上 hp=2   → 死 54 次 / 900s 没打完
```

**只要有一关残血通关，后面整局锁死在那个血量上**，而游戏没有任何回血手段
（`respawn()` 回满血只用于落水）。DESIGN §8 没规定死亡时血怎么处理，所以这是**没定过的规则**，不是实现 bug。
涉及 `src/core/save.js` 与 `src/entity/player.js`（T2），我一行没动。

### 9.2 第五回 Boss：无锋「学会了但装不上」，Boss 变成完全无敌 —— 需要裁定

`Tech.learn` 只往**空槽**里塞（tech.js:822）。一周目走到第五回时四个槽通常已经满了：

```
出第4关 known=[poyu,chengtian,tiyun] slots=[poyu,chengtian,tiyun,null]
第五回内 学会 fenshu  → slots 塞满
第五回内 学会 chuanyang → 无空槽，没装上
第五回内 学会 wufeng    → 无空槽，没装上
守阁人 block(): openT<=0 时只有 moveId==='wufeng' 能撬开，其余一律挡掉
→ Boss 320 血，一滴不掉（实测 32000 帧）
```

真人必须自己想到「进暂停菜单 → 换招 → 把无锋换上去」。游戏没有任何提示（DESIGN §0 铁律 3 不做教程弹窗），
而这是全游戏唯一一个「不换招就打不过」的 Boss。用户已经在第一回 Boss 抱怨过「打不过」——这一处比那处硬得多。
涉及 `src/combat/tech.js`（T2）/ `src/ui/menus.js`（T4）。

### 9.3 `updateWaves` 一次只跑一波：没有 gate 的波会把后面所有波静默吃掉

`if (R.active) { …; return; }`。第五回第 2 波没有 gate，玩家可以绕过去把它的敌人留在原地 ——
只要还有一个活着，**第 3 波（Boss 前 3 人，gate [3500,4060]）就永远不刷**。
实测机器人把一个僧人打到 1 血就走了，整场再没见过第 3 波。不报错，玩家也不会察觉自己少打了一场。
不是软锁，但是「关卡内容静默消失」。改法涉及波次语义 = 玩法，等你定。
